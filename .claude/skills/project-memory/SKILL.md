# Память проекта

## В конце задачи (1–3 минуты)
1. **STATE.md** — заменить разделы по факту: «Сейчас» (работает / в работе / следующий шаг
   с файлом), дата и `head:` = `git rev-parse --short HEAD` (STATE пишется до коммита, поэтому
   `head:` отстаёт на один коммит — это норма), «Ждёт владельца»
   (решения, допущения), «Тупики» (что пробовали и отвергли — чтобы не повторять).
   Историю не копить; то, что есть в git или SPEC, — ссылкой.
2. **KNOWLEDGE.md** — «Доступы»: новый сервис, учётная запись, ключ — строкой сразу (имя в
   `.env`, где настраивается, статус); значения не записывать. Дальше — факт, договорённость,
   термин («как называть / как не называть»),
   найденный ответ с источником и датой. Нашлось точнее — исправить строку, не добавлять вторую.
3. **LESSONS.md** — ошибка, которой можно было избежать: фильтр «без этой строки следующий
   сеанс повторит ошибку, читая только код?» Нет — не писать. Область: «общий» (верно для любого
   проекта, без имён этого кода и данных) или «проект». Новая → «кандидат» (после «да»);
   уже есть → повторов +1, «активен»; повтор при активном → предложить хук/тест/линтер,
   после внедрения «закрыт», строку сжать. Сложная решённая проблема с деталями →
   `docs/ai/solutions/<slug>.md` по `_TEMPLATE.md`, в LESSONS — только вывод.
   Сообщения коммитов: `feat: / fix: / docs: / chore: <что сделано по-русски>`.
4. **DECISIONS.md** — только если все три: дорого отменить, удивит без контекста, был
   реальный выбор. «Сборка доказала: …» — когда план ошибся.
5. **PROJECT_MAP.md** — если изменились области, правила размещения или команды (только
   запущенные); зоны «не трогать» — в PROFILE.md. **TOOLS.md** — установлено/удалено.
   **SPEC.md** — статусы требований. **FOUNDATION.md** — стиль/компоненты.
6. Всё это — молча, владельцу не сообщать. Дату и `head:` в STATE.md хук ставит сам.

## Рост документов: когда заводить новый
- Заводить `docs/ai/<ТЕМА>.md` (латиницей, по теме: `API_YANDEX.md`, `DEPLOY.md`,
  `DATA_SCHEMA.md`, `SCREENS.md`), когда: тема в KNOWLEDGE больше 10 строк; одно и то же
  ищется второй раз; появился внешний сервис, база, сервер, деплой или общие правила экранов.
  Перенести туда накопленное, из KNOWLEDGE убрать.
- Сразу строка в `docs/ai/INDEX.md`: файл · какие данные в нём · когда читать. Всё молча.
- Предел: PROFILE 40 строк, STATE 60, KNOWLEDGE 80, LESSONS 40, INDEX 60, остальные 300.
  Переполнен → отдельная подтема в свой файл; продолжение той же темы — `<ТЕМА>_2.md`,
  `_3.md`; в INDEX у каждой части — какие именно данные в ней, чтобы читать только нужную.
  Хук при завершении ответа проверяет пределы и запись в INDEX.
- Правило для части кода → `.claude/rules/<тема>.md` с `paths:`. Повторяемая процедура →
  скилл. Крупная часть проекта со своими правилами → вложенный `<часть>/CLAUDE.md`.
- Скилл не сработал сам → строка в LESSONS; повтор → уточнить его `description`
  (триггерные фразы первыми).

## Что писать и что нет
Писать: намерения, причины, договорённости, грабли, команды, которые нельзя угадать.
Не писать: видное из кода (перечни файлов, зависимостей, структура папок, описание функций)
и догадки как факты (пометка «не проверено»).

## Гигиена
- Блок набора в CLAUDE.md ≤ ~120 строк, весь файл ≤ 200 (длинный файл слушается хуже
  короткого); пределы docs/ai — выше, «Рост документов», хук их проверяет; PROJECT_MAP ≤ 40.
- Правки точечные, не переписывать целиком (при пересказе теряются детали).
- Раз в ~10 задач или по просьбе — ревизия: тест «убери строку — изменится ли поведение?
  нет — удалить»; устаревшее удалить; дубли слить; противоречия показать владельцу;
  сравнить размер CLAUDE.md с лимитом выше; неиспользуемые скиллы и инструменты — по TOOLS.md.
- Факты — из кода, проверок и git, не из памяти.
