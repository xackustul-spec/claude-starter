# Поиск решения: $ARGUMENTS

Цель — проверенное решение из внешних источников, а не угадывание.

## 0. Сначала своё
`docs/ai/LESSONS.md`, `docs/ai/solutions/` (поиск по симптому), KNOWLEDGE «Ответы, которые уже искали».

## 1. Факты до поиска
- Точный текст ошибки (первые и последние строки трассировки), без секретов и личных данных.
- Версии: язык и рантайм, ключевые пакеты (lock-файл проекта или команда менеджера пакетов),
  ОС, где это работает (локально / сервер / контейнер).
- Что уже пробовали и что изменилось перед ошибкой (`git log -5`, `git diff`).

## 2. Искать по порядку (≤3 запроса на источник)
1. Context7 (если подключён; иначе официальный сайт) — документация *нашей* версии.
2. Официальная документация, changelog, руководство по миграции — breaking changes.
3. GitHub Issues проекта (`gh search issues`, без `gh` — веб-поиск `site:github.com <проект> <ошибка>`):
   закрытые issues и чем закрыты (коммит, версия).
4. Stack Overflow, Habr, форумы — по тексту ошибки без путей и чисел нашей машины.

## 3. Оценить найденное
Совпадают версия и окружение? Решение подтверждено (принятый ответ, закрытый issue, релиз с
фиксом)? Свежее (быстро меняющаяся библиотека — не старше 2–3 лет)? «Отключить проверку /
подавить предупреждение» не брать, если есть решение причины.

## 4. Отчёт владельцу до изменений
Причина (1–2 предложения) · 1–3 варианта: что сделать, риск, источник и версия ·
«Рекомендую: …». Зависимости, база или больше 1–2 файлов → менять после «да» (при полном
доверии — сразу, установки через `compat-check`). После исправления — проверка и её вывод.
Найденный ответ → KNOWLEDGE «Ответы»; сложный случай → `docs/ai/solutions/<slug>.md`;
урок → LESSONS (после «да»).
