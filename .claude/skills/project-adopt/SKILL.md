# Подключение к работающему проекту

Не ломать. Код приложения не менять. Документы и правила владельца не удалять и не
переписывать без «да». Ничего не устанавливать; тесты запускать только если зависимости
уже стоят (иначе — записать как риск).

## 1. Изучить (только чтение; крупный проект — субагентами по областям, ≤3 параллельно)
- Структура, стек и версии, точки входа, как запускается, тесты, деплой, где база и секреты
  (только имена), CI. `git log --oneline -30`, `git log --stat -50` — горячие места и
  повторяющиеся `fix:` (это будущие уроки). Нет git — первый риск.
- Существующие инструкции: CLAUDE.md, AGENTS.md, README, docs/, ТЗ, `.claude/` (скиллы,
  настройки, хуки), `.mcp.json` (имена серверов); `/memory`, `/mcp`, `/plugin` — попросить
  владельца показать.

## 2. Слить инструкции (показать разницу → «да»)
- Есть CLAUDE.md владельца (набор лежит как `CLAUDE.starter.md`): содержимое набора вставить
  внутрь маркеров `<!-- claude-starter:start -->` … `<!-- claude-starter:end -->`, обязательно
  вместе со строками `@docs/ai/…` из начала `CLAUDE.starter.md` (без них PROFILE, STATE,
  KNOWLEDGE, LESSONS не загрузятся);
  текст владельца вне маркеров не трогать; повторный запуск заменяет блок, а не дублирует.
  Противоречия (например «показывать полный код» против профиля) — показать владельцу
  и спросить, что главнее; до ответа действует правило владельца.
- Есть AGENTS.md, `.cursor/rules`, copilot-instructions — подключить строкой `@<путь к файлу>`
  (или предложить владельцу `/import`), не переписывать. AGENTS.md есть, CLAUDE.md нет → CLAUDE.md =
  строка `@AGENTS.md` + блок набора.
- Есть `.claude/settings.json` владельца (набор лежит как `settings.starter.json`): слить
  разрешения и хуки, чужое не удалять; после «да» starter-файл удалить. ОС не Windows →
  хуки из `settings.unix.json`. Изменения хуков подхватываются сами — сразу живая проверка
  из `kit-setup` шаг 3 (`_test.ts` с `const ПРОБА = 1` блокируется). Перезапуск сеанса
  нужен только для `env` (уровень доверия) — попросить владельца в конце скилла.
- Большие документы проекта (ТЗ, состояние, чек-листы) не копировать — строкой в
  `docs/ai/INDEX.md`: для чего, когда читать (поиском по разделу). Свои документы набора, которые
  дублируют существующие, — не заводить, сослаться.
- README.md и `.gitignore` проекта не заменять; недостающие строки `gitignore.starter` — добавить.

## 3. Заполнить docs/ai — только тем, чего не видно из кода
Фильтр каждой строки: «Claude ошибётся без неё, читая только код?» Нет — не писать.
- PROFILE.md: паспорт и зоны «не трогать» (старый код, чужие модули, сгенерированное;
  что стабильно, что экспериментально). STATE.md: по факту, `head:`.
- PROJECT_MAP.md: области и правила размещения, команды — только запущенные
  (запуск, тесты все / один файл / один тест, с чистым выводом). Перечень файлов не вести.
- SPEC.md: особые требования (персональные данные, платежи, закон) — если они есть в документах.
- LESSONS.md: повторявшиеся ошибки из истории и памяти (статус по числу повторов).
- KNOWLEDGE.md: договорённости, термины (как называть и как не называть), факты окружения.
- TOOLS.md (что уже стоит), DECISIONS.md (что видно из кода и документов, с пометкой
  «выведено из кода — не проверено владельцем»).

## 4. Распространить по проекту (с «да»)
- Крупная часть со своим стеком или правилами (например `web/`, `worker/`, пакет монорепо)
  → вложенный `<часть>/CLAUDE.md` на 5–15 строк: назначение, команды, свои правила,
  «не трогать». Подгружается сам, когда Claude работает с файлами в этой папке.
- Правила для типов файлов уже в `.claude/rules/`; специфичное для проекта — дописать туда.
- Шапки `Назначение:` — только при изменении файла, не массовой правкой (хук напомнит).

## 5. Защиты — списком, делать по одной с «да»
git и `.gitignore` · тест на самую важную логику (особенно на повторявшуюся ошибку) ·
бэкап базы · хук на ошибку, повторившуюся дважды · секреты вне репозитория.

## 6. Обзор и вопрос владельцу — обязательный шаг
Разбор не заканчивается списком: он заканчивается вопросом по теме проекта. Порядок:
Предложения — про сам проект: чтобы он стал шире, мощнее, удобнее и заметнее. Разовые задачи
(«посчитать», «сделать отчёт») владелец ставит сам — их не предлагать.
3–5 находок в формате «вижу X → предлагаю Y → что даст → риск», по этим направлениям:
- **Вид и удобство**: экраны собраны вручную → показать несколько библиотек компонентов в
  HTML-превью (все варианты сразу, с темами) и перевести интерфейс на выбранную.
- **Возможности**: чего нет у нас, но есть у похожих сервисов (1–2 поиска) — уведомления,
  поиск, фильтры, импорт и выгрузка, роли и доступы, мобильный вид, печать.
- **Данные и интеграции**: что можно подтянуть автоматически вместо ручного ввода (почта,
  банк, аналитика, календарь, мессенджер, сканирование документов).
- **Уникальность**: что даст проекту преимущество — автоподсказки, автопроверки,
  генерация текстов и изображений, отчёты «сами собой», голосовой ввод.
- **Надёжность и скорость**: бэкап базы, тесты на самое ценное, один скрипт выкладки,
  медленные места из истории коммитов.

Предлагать по типу проекта (готовые наборы — `.claude/skills/tool-scout/packs.md`):
- сайт, лендинг, портфолио → анимация и эффекты прокрутки, 3D-сцены, видеофон и генерация
  роликов, оптимизация фото, быстрые страницы, SEO и превью для соцсетей, формы заявок;
- панель, CRM, учёт → таблицы с фильтрами и сортировкой, графики, выгрузка в Excel и PDF,
  импорт из файлов и почты, права и журнал действий, поиск по всему;
- магазин → корзина и оплата, доставка, отзывы, рекомендации, карточки товара с фото и 3D;
- бот, рассылки → сценарии, очередь сообщений, шаблоны, статистика ответов;
- обработка документов и данных → распознавание, сверка, автозаполнение, отчёты по расписанию. Затем — прямой вопрос с пронумерованными вариантами из находок, по-русски и по теме проекта,
например: «Чем усилим проект первым: 1 — единый вид всех экранов на одной библиотеке (покажу
варианты), 2 — импорт выписок из банка вместо ручного ввода, 3 — уведомления клиентам,
4 — своё?»
Ответ владельца → `tool-scout` (подбор и проверка) → установка только после «да».
В STATE.md записать строку «разбор возможностей сделан: <дата>», чтобы не повторять его каждый сеанс.

## 7. Отчёт (сжато, каждый раздел с «Рекомендую: …»)
Что за проект (5 строк) · что создано/дополнено · противоречия, ждущие решения · риски ·
вопросы · «Заметил, не сделал». `CLAUDE.starter.md`/`settings.starter.json` после слияния удалить (с «да»).
