# Новая функция: $ARGUMENTS

По этапам; переход дальше — после «ок» там, где указано.

## Этап 1. Понять и определить размер
- Сначала размер, потом чтение. **Малая** — вкладка, кнопка, столбец, фильтр, поле, отчёт на уже
  имеющихся данных, один экран: таблицы и поля под неё уже есть либо добавляется одно-два.
  **Крупная** — новый поток работы, несколько экранов, новые таблицы или перенос данных, настройки,
  внешняя служба. Сомневаешься — малая: вырастет по ходу — скажешь.
- Малая: места в коде найти самому — `PROJECT_MAP.md` и 2–3 поиска по имени таблицы или шаблона;
  субагента на разведку не звать (он стоит 2–3 минуты, а читать тут три файла). ТЗ — 3–5 строк
  в ответе, слова владельца — одной цитатой в `SPEC.md`; отдельного файла ТЗ нет. Делать сразу,
  «ок» ждать только при открытом вопросе. Этапы 2 и 3 пропустить.
- Крупная: нужный раздел `SPEC.md` и `PROJECT_MAP.md` — самому, обход кода — субагентом.
- Вопросы — по правилам `project-intake` §2: только закрывающие требование, с рекомендуемым
  вариантом, сначала блокирующие; крайние случаи — пусто, ошибка, большие объёмы, повторный
  запуск, первый запуск, прерывание, права, откат. Что решает владелец: деньги/сервис,
  что он видит, отмена = переделка, правила его бизнеса. Нет вопросов — сказать и идти.

## Этап 2. ТЗ → «ок» (только крупная)
`docs/ai/specs/<ГГГГ-ММ-ДД>-<slug>.md` (+ строка в SPEC.md), **не длиннее 40 строк**: исходные
слова владельца короткими цитатами (до 12 слов); требования Т1… с цитатами, каждое проверяемое; анти-цели; затронутые
файлы и таблицы — списком путей, без пересказа кода (что уже есть, видно из кода — в ТЗ это не
переписывать); сквозной сценарий проверки; открытые вопросы и `TODO(данные)`.
Самопроверка: нет «уточнить» без владельца; разделы не противоречат; ни одно Т нельзя
понять двумя способами; объём — одна функция. Показать → **ждать «ок»**.

## Этап 3. План → «ок»
Шаг = узкий сквозной срез (данные → логика → экран → тест), который можно показать; не
«сначала вся база, потом весь интерфейс». У шага: какие Т закрывает (шаг без Т — работа,
которую никто не заказывал: убрать), что отдаёт следующим (имена, сигнатуры), как проверить.
Проверка в обе стороны: каждое Т — хотя бы в одном шаге, каждый шаг — из Т.
Показать → **ждать «ок»** (только для крупной задачи по CLAUDE.md; не крупную — делать сразу).

## Этап 4. Сделать
Новые библиотеки → `compat-check`. Шаг, меняющий один файл, — `safe-change` шаги 4–6;
шаг с переносами, данными, конфигурацией, общим стилем — полный `safe-change`.
Тест сначала (если в проекте есть тесты) → код → проверка → коммит. Не получается после
двух попыток — стоп, `find-solution`, сообщить. План не работает → сказать и предложить
правку ТЗ, требования молча не менять.

## Этап 5. Приёмка
- Слепая приёмка: субагенту `change-verifier` — только исходные слова владельца из SPEC
  и репозиторий, без ТЗ и плана; запустить проект и пройти сценарий, не только читать код.
  Интерфейс — `ui-checker`. Расхождения → в отчёт, не править молча.
- Все проверки, вывод показать. Отчёт: таблица Т → готово / частично / нет + как проверено.
- `project-memory` (STATE, KNOWLEDGE, LESSONS); замеченное рядом — строкой в STATE.md, «Заметил».
