# Разбор проекта

Цель — до первой строки кода ясно: что строим, для кого, из чего, как проверим.

## 0. С чего начать (одна строка владельцу)
«Расскажите о проекте сами или задать вопросы? 1 — задавайте вопросы (рекомендую),
2 — расскажу сам.» Ответ «1» — вести разговор по шагам 1–2, по одному-два вопроса за раз,
начиная с самого главного: что за проект, для кого, что человек делает в нём по шагам.
Ответ «2» — выслушать рассказ, потом задать только то, чего не хватает.

## 1. Понять (сначала самому)
Из рассказа, брифа, референсов выписать: цель и результат; пользователи и сценарии по
шагам; платформа (сайт / веб-приложение / мобильное / Telegram / внутренний сервис);
данные — какие, откуда, персональные / медицинские / платёжные (→ требования закона:
хранение, согласия); интеграции (оплата, календарь, CRM, почта, мессенджеры, карты,
аналитика); визуал (референсы, фирменный стиль, анимация, видео, 3D, фото);
ограничения (бюджет на сервисы, хостинг, сроки, кто будет поддерживать).
Как это делают существующие сервисы — 1–2 поиска, чтобы спросить про отличия.
Проект уже с кодом и набор не подключён (в PROFILE.md TODO) → предложить владельцу ввести
`/kit-setup`; самому разбор не начинать. Подключён — разбирать новую крупную часть.

## 2. Спросить (не больше 3 раундов)
- Каждый вопрос закрывает конкретное требование или блокирующую неизвестность:
  платформа, где живут данные, оплата, хостинг, вход пользователей. Вопрос «для порядка»
  не задавать. Нет вопросов — сказать «в задаче всё однозначно» и идти дальше.
- Что решает владелец, а не Claude: стоит денег или привязывает к сервису; меняет, что он
  видит и может; отмена = переделка; правило его бизнеса (цены, сроки, права).
  Остальное (тексты ошибок, повторы, лимиты) — решить самому и записать в STATE «Допущения».
- По одному, если ответ влияет на следующий; иначе до 3–4 разом; у каждого — вариант
  «(Рекомендую)». Ответ «не знаю» → взять рекомендуемый, записать как допущение.
- Ответ записывать в SPEC сразу, не в конце разговора. За количество вопросов не извиняться.
- Проверка идеи (1–2 вопроса, если по делу): что сломается через месяц (рост, дубли,
  поддержка)? кто ещё будет пользоваться? какие два требования не могут быть верны
  одновременно?
- Эталон: «на что должно быть похоже — 2–3 примера» → SPEC «Эталон», только со слов владельца.

## 3. Записать → «ок»
- `docs/ai/SPEC.md`: требования Т1… с цитатами владельца, анти-цели, эталон, стек
  (предложение → «ок»), сквозной сценарий проверки. Самопроверка перед показом: нет
  «уточнить» без владельца, разделы не противоречат, ни одно Т нельзя понять двумя способами.
- Паспорт в `docs/ai/PROFILE.md`; решения — DECISIONS.md; факты — KNOWLEDGE.md.
- Всё, что можно показать (структура экранов, схема данных, пример отчёта) — HTML-превью
  или картинка в `docs/ai/previews/`.
- Коммит `docs: ТЗ …`.

## 4. Карта возможностей → дальше
| Возможность | Зачем (Т№) | Чем закрывают: библиотека / сервис / скилл / MCP |
Кроме заказанного — 2–3 возможности «сверх просьбы», которые сделают проект шире или
заметнее (что есть у похожих сервисов, чего просили бы пользователи), с пометкой «предложение».
Например: единый стиль и готовые экраны → дизайн-система; видео → генерация/сжатие;
фото → оптимизация; 3D → three.js; вход → библиотека авторизации; платежи → сервис.
Дальше: интерфейс есть → `project-foundation`; инструменты для Claude → `tool-scout`
(сначала базовый набор: браузер для проверки, LSP языка, git); выбранное → `compat-check`.

## 5. Итог владельцу (сжато)
Что поняли · что предлагаем (стек, каркас, инструменты) · что нужно от владельца
(решения, доступы, бюджет) · «Заметил, не сделал» (1–3 идеи сверх просьбы).
