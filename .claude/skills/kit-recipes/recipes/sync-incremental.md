# Как забирать новые данные из MS SQL в Postgres

Описание действующего метода для передачи в другой проект. Составлено
03.10.2026 по работающей системе: 1С на MS SQL → наш Postgres, 16 модулей
синхронизации, непрерывная работа с августа 2026.

---

## 1. Условия задачи

**Источник** — база 1С на MS SQL Server. Чужая, рабочая, менять в ней нельзя
ничего. Доступ только на чтение, отдельной учётной записью с правами
`SELECT`.

**Приёмник** — свой Postgres. Пишем только в него.

**Требование** — данные в приёмнике должны обновляться почти сразу, но
источник нельзя нагружать: это боевая база, в которой работает клиника.

**Главное ограничение, из которого растёт весь метод:** в источнике нельзя
создать ни триггер, ни таблицу-журнал, ни временную таблицу. Значит
«подписаться на изменения» классическим способом невозможно — остаётся только
спрашивать.

---

## 2. Идея

Спрашивать «что изменилось», а не «дай всё».

Полный перечит справочника клиентов — это 36 тысяч строк каждые пять секунд.
Такое источник не выдержит, и 99,9% этой работы бесполезны: между двумя
опросами меняются две-три записи.

Поэтому синхронизация состоит из двух шагов:

1. **дёшево узнать список изменившихся записей** — вернулись только
   идентификаторы, несколько десятков байт;
2. **забрать полные данные только по этому списку** — тем же самым рабочим
   запросом, что использовался бы для полного прогона, просто с фильтром
   `WHERE _IDRRef IN (...)`.

Второй шаг — ключевой приём. Бизнес-логика запроса (соединения со
справочниками филиалов, врачей, скидок) пишется **один раз** и работает и для
полного прогона, и для инкрементального. Два разных запроса неизбежно
разъедутся.

---

## 3. Шаг первый: как узнать, что изменилось

### Способ А. Change Data Capture — если он уже включён

В MS SQL есть встроенный механизм CDC: сервер сам ведёт журнал изменений
таблицы и позволяет спросить «что менялось между двумя точками». Точка
называется **LSN** — порядковый номер в журнале транзакций.

**КРИТИЧЕСКИ ВАЖНО.** Мы CDC **не включаем**. В нашем случае он уже был
включён владельцем базы для своих задач, и мы только читаем его результат.
Вызывать `sp_cdc_enable_table` на чужой базе 1С нельзя: это изменение объектов
базы, которое меняет её поведение и может сломать обновление конфигурации.
Если CDC не включён — это вопрос к владельцу базы, а не к разработчику
синхронизации. Пока его нет, работает способ Б.

Как пользуемся:

```python
# текущая точка журнала на сервере-источнике
def get_max_lsn(mssql_conn) -> bytes:
    cur = mssql_conn.cursor()
    cur.execute("SELECT sys.fn_cdc_get_max_lsn()")
    lsn = bytes(cur.fetchone()[0])
    cur.close()
    return lsn


# какие записи изменились между прошлой точкой и текущей
def get_changed_ids(mssql_conn, source_table, id_field, last_lsn, current_lsn):
    """Возвращает множество идентификаторов, изменившихся в диапазоне
    (last_lsn, current_lsn]. None означает «первый запуск, нужен полный
    прогон»."""
    if last_lsn is None:
        return None

    capture_instance = f"dbo_{source_table}"
    cur = mssql_conn.cursor()
    cur.execute(
        f"SELECT DISTINCT [{id_field}] "
        f"FROM cdc.fn_cdc_get_all_changes_{capture_instance}(?, ?, 'all')",
        last_lsn, current_lsn,
    )
    ids = {bytes(row[0]) for row in cur.fetchall() if row[0] is not None}
    cur.close()
    return ids
```

Поле идентификатора зависит от вида объекта: у справочников и документов это
`_IDRRef`, у регистров накопления — `_RecorderRRef` (ссылка на документ-
регистратор).

Запрос возвращает только идентификаторы — он лёгкий даже когда изменений
много.

### Способ Б. Скользящее окно по дате — когда CDC недоступен

Если журнала изменений нет, остаётся опираться на даты внутри самих данных.
Берём не всю таблицу, а последний отрезок времени:

```sql
-- записи на приём: только будущие, прошлое не меняется
WHERE DATEADD(YEAR, -2000, doc._Fld3096) >= CAST(GETDATE() AS DATE)

-- выработка: скользящее окно назад на N месяцев
WHERE DATEADD(YEAR, -2000, r._Period) >= DATEADD(MONTH, -3, GETDATE())
```

Этот способ проще, но грубее: он перечитывает весь отрезок целиком, поэтому
такие модули запускаются реже — раз в полчаса или раз в час, а не каждые пять
секунд. У нас так работают 11 модулей из 16: прайс, расписание смен,
выработка, справочник сотрудников и другие медленно меняющиеся данные.

Выбор между А и Б решается просто: **есть CDC — берём А, нет — берём Б с
подходящей частотой.** Смешивать в одном модуле не нужно.

## 4. Шаг второй: забрать данные по списку

Полученные идентификаторы подставляются в рабочий запрос. В MS SQL они
бинарные, поэтому превращаются в шестнадцатеричные литералы:

```python
def hex_list_sql(ids: set[bytes]) -> str:
    """Фрагмент "0x.., 0x.., ..." для подстановки в IN (...).
    Пустой список даёт заведомо несуществующий 0x00, чтобы запрос вернул
    ноль строк, а не упал на пустых скобках."""
    if not ids:
        return "0x00"
    return ", ".join("0x" + i.hex().upper() for i in ids)
```

Дальше в запросе — одно место, которое меняется:

```python
sql = BASE_QUERY
if id_filter_sql:
    sql += f" AND c._IDRRef IN ({id_filter_sql})"
```

**Ограничение, о котором надо знать заранее:** MS SQL не принимает больше
примерно 2100 параметров в запросе, а очень длинный `IN (...)` сам по себе
начинает тормозить. Если за интервал изменилось больше нескольких тысяч
записей — проще сделать полный прогон, чем перечислять. У нас это случается
только после ежемесячного сброса, и там полный прогон и так предусмотрен.

## 5. Где хранится состояние

**В своём Postgres, не в источнике.** Это принципиально: в чужую базу мы не
пишем ничего.

```sql
CREATE TABLE IF NOT EXISTS sync_cdc_state (
    source_table TEXT PRIMARY KEY,
    last_lsn     BYTEA,
    updated_at   TIMESTAMPTZ DEFAULT now()
);
```

Одна строка на таблицу-источник. Отсутствие строки означает «никогда не
синхронизировали» и запускает полный прогон — тот же самый код, просто без
фильтра. Отдельной ветки «первый запуск» писать не нужно.

**Точка сохраняется только после успешной записи данных.** Если модуль упал
на середине, состояние остаётся старым, и следующий заход заберёт тот же
диапазон заново. Повторная обработка безопасна — об этом следующий раздел.

---

## 6. Запись в Postgres: повторный прогон не должен ломать данные

Всё пишется через `INSERT ... ON CONFLICT DO UPDATE` по идентификатору из
источника:

```sql
INSERT INTO patient_profiles (external_1c_id, full_name, ...)
VALUES %s
ON CONFLICT (external_1c_id) DO UPDATE SET
    full_name  = EXCLUDED.full_name,
    ...
    updated_at = now()
```

Это даёт главное свойство: **один и тот же диапазон можно обработать сколько
угодно раз с одинаковым результатом.** Поэтому не страшны ни падение посреди
работы, ни перезапуск контейнера, ни повторный запуск руками.

Пакетная вставка — через `psycopg2.extras.execute_values`, а не построчно:
тысяча отдельных `INSERT` работает в сотни раз медленнее одного пакета.

## 7. Чем всё это крутится

Один вечный процесс в Docker с `restart: unless-stopped`. Не cron: cron даёт
минутную гранулярность и неприятно ведёт себя, когда предыдущий запуск ещё не
закончился.

```python
def run_safely(name, fn):
    """Одна упавшая синхронизация не должна останавливать остальные."""
    try:
        fn()
    except Exception:
        log.exception("Синхронизация '%s' упала с ошибкой, продолжаю цикл", name)


def main():
    while True:
        run_safely("clients", sync_clients.main)
        run_safely("procedures", sync_procedures.main)
        ...
        time.sleep(INTERVAL_SECONDS)   # у нас 5 секунд
```

**У каждого модуля своя частота.** Цикл крутится раз в пять секунд, но
тяжёлые модули столько раз в секунду не нужны:

```python
ЧАСТОТА = {
    "doctor_output":     3600,   # выработка, 29 тыс. строк
    "doctor_shifts":     1800,
    "staff":             1800,
    "medical_protocols":  600,
}

def run_periodic(name, fn):
    """Запускает модуль не чаще заданного. Первый заход после старта —
    сразу, дальше по своему интервалу."""
    интервал = ЧАСТОТА.get(name)
    if интервал is None:
        return run_safely(name, fn)
    сейчас = time.monotonic()
    прошлый = _последний_запуск.get(name)
    if прошлый is not None and (сейчас - прошлый) < интервал:
        return
    _последний_запуск[name] = сейчас
    return run_safely(name, fn)
```

Без этого ограничителя выработка перечитывалась из источника около 6000 раз в
сутки — чистая нагрузка впустую на обе базы.

Отдельно — суточные задачи (ночные пересчёты) с отметкой в таблице
`sync_daily_state`, чтобы они выполнялись раз в день, а не на каждом обороте
цикла.

## 8. Ежемесячная полная сверка

Инкрементальная синхронизация со временем накапливает расхождения: пропущенный
диапазон, ошибка в одном прогоне, изменение, не попавшее в журнал. Поэтому
первого числа каждого месяца состояние сбрасывается целиком:

```python
def check_and_perform_monthly_reset(pg_conn):
    today = date.today()
    if today.day != 1:
        return
    # маркер, чтобы не сбрасывать повторно на каждом обороте цикла
    ...
    cur.execute("DELETE FROM sync_cdc_state")
```

Следующий заход каждого модуля видит отсутствие состояния и делает полный
прогон. Отдельного кода для этого писать не надо — он уже есть, тот же, что
для первого запуска.

---

## 9. Что нужно на стороне источника

1. **Учётная запись только на чтение.** Это техническая гарантия того, что
   синхронизация физически не может ничего испортить. Не «мы договорились
   писать только SELECT», а именно права.
2. **CDC, если его хотят использовать** — включает владелец базы, не мы.
3. **Сетевой доступ** к MS SQL с машины синхронизации.

Больше ничего. Ни таблиц, ни процедур, ни триггеров в источнике не создаётся.

## 10. Подводные камни, на которых мы потеряли время

**Даты в 1С смещены на 2000 лет вперёд.** Везде нужен
`DATEADD(YEAR, -2000, поле)`. Забыли — получите 4026 год и пустую выборку.

**Суффикс `X1` в именах таблиц.** В одной базе одновременно существуют
`_Document316` (0 строк) и `_Document316X1` (418 строк). Любое имя проверять в
обоих вариантах через `sys.tables`, прежде чем писать запрос.

**Часовой пояс.** Каждое подключение к Postgres начинается с
`SET TIME ZONE 'Europe/Moscow'`, иначе время уедет на три часа.

**Имена полей в 1С описывают намерение, а не поведение.** Поле может
называться «врач» и содержать того, кто заполнял документ. Доверять надо
данным, а не названию: проверять выборочно и сверять с интерфейсом 1С.

**Колонки результата сверять по имени, а не по номеру.** Порядок колонок
меняется при правке запроса, и молчаливая подмена одного поля другим
обнаруживается через недели.

**Один объект может иметь несколько связанных карточек.** У нас у сотрудника
может быть несколько учётных записей пользователя — по одной на филиал.
Соединение по ним даёт дубли строк, и выбирать одну «наугад» нельзя: нужные
данные могут оказаться в любой. Либо собирать по всем сразу, либо сворачивать
дубли осознанно, по полноте записи.

**Код внутри Docker-образа.** Если сборка без volume, правка файла на диске ни
на что не влияет до пересборки. После правки — обязательно проверить, что
новый код действительно внутри контейнера.

**После изменения логики модуля** сбросить состояние по его таблице, иначе
исправление ляжет только на новые записи, а уже загруженные останутся
кривыми.

## 11. Чего этот метод не делает

**Не ловит удаления.** CDC их показывает, но если объект в источнике помечен
на удаление или физически удалён, в приёмнике он останется, пока это не
обработано отдельно. У нас помеченные на удаление отсекаются условием
`_Marked = 0x00` в самом запросе, и при полном месячном прогоне они уходят.

**Не даёт мгновенности.** Задержка равна интервалу цикла — у нас до пяти
секунд для важного и до часа для медленного. Если нужна настоящая мгновенность,
это уже очередь сообщений, а не опрос.

**Не защищает от изменения структуры источника.** Переименовали поле в
конфигурации — модуль упадёт. Это ловится прогоном проверок, а не самой
синхронизацией.

## 12. Сухой остаток, если передавать одним абзацем

Вечный процесс опрашивает источник. Для каждой таблицы он сначала спрашивает
дёшево — «какие записи изменились с прошлой точки», запоминая точку в своей
базе, а не в чужой. Потом забирает полные данные только по полученному списку
тем же запросом, что использовался бы для полного прогона. Пишет через UPSERT,
поэтому повтор безопасен. Точка сохраняется только после успешной записи.
Раз в месяц точки сбрасываются, и всё перечитывается целиком — как страховка
от накопленных расхождений. В источнике не создаётся ничего, учётная запись
имеет права только на чтение.
